Why are we doing this?

An AI can install software, add up numbers and write proofs faster than either of us ever will. So why learn any of it?

For the same reason people learned pure math long before anyone needed it. Almost nobody uses calculus at work. What it built was the ability to understand: to follow an argument, see why it holds, and notice when it doesn’t.

That’s the point of this course: not to get the computer to do things, but to understand what it did, and why, well enough to catch it when it’s wrong.

To check your understanding as you go, guess what each command will do before you run it. When the computer surprises you, that’s the interesting part: guess why, in your own words, check with Claude, and ask your teacher for help.

TipHow to use this page

This lesson is twelve short days, each one sitting of 15 to 30 minutes: setting up (days 1–3), Python (4–7), adding up 1 to 100 (8–10) and Lean (11–12). Do one day, stop whenever you like, and come back: the list of days at the top of the page shows where you are and takes you back there.

Each grey box has a copy button in its top right corner. Paste into the terminal with Ctrl+Shift+V and press Enter. Read the sentence above each box before you run it.

Day 1: Turn on Linux (~20 min)

Turn on Linux (WSL)

Underneath the windows and buttons, a computer works with text. A terminal is a window where you talk to it in words. We’ll use Linux, running inside Windows (that’s WSL, Windows Subsystem for Linux).

  1. Click Start and type PowerShell.
  2. Right-click Windows PowerShell, choose Run as administrator, and click Yes.
  3. Paste this and press Enter:
wsl --install

When it says so, restart the computer. A window called Ubuntu (our kind of Linux) then opens and asks you to make up a username (short, lowercase, no spaces) and a password.

WarningThe password is invisible

When you type it, nothing appears, not even dots. That’s normal. Type it anyway and press Enter.

From now on, open Terminal from the Start menu and pick Ubuntu from the ▾ menu next to the tabs.

Look around

The line ending in $ is the prompt: the computer waiting for you.

pwd

pwd prints where you are, something like /home/anna: your home folder, written as a path (folders inside folders, separated by /).

mkdir course
cd course
pwd

Before the last line, guess what pwd will print now. (mkdir makes a folder, cd goes into one, cd .. goes up a level.)

Stop the password questions

Commands starting with sudo run as the administrator, and Linux asks for your password each time. The Windows login already protects this computer, so we tell Linux to stop asking:

echo "$USER ALL=(ALL) NOPASSWD:ALL" | sudo tee /etc/sudoers.d/$USER
sudo chmod 0440 /etc/sudoers.d/$USER

Day 2: Get a tutor (~20 min)

Your tutor: Claude Code

Claude is an AI, a language model: it learned from a huge amount of text to predict what words come next. That turns out to be enough to explain things and write code. It also makes Claude very good at sounding right. Usually it is right. Sometimes it isn’t, and it can’t always tell. That’s why you check.

Claude Code lets you talk to Claude in the terminal. You’ll need a Claude account.

curl -fsSL https://claude.ai/install.sh | bash

curl downloads the installer, and | bash runs it (the |, a pipe, sends one command’s output into the next).

Claude could do this whole lesson by itself. That’s why we tell it not to. This box writes a file called CLAUDE.md: standing instructions Claude reads every time it starts in this folder.

cat > ~/course/CLAUDE.md <<'EOF'
# Tutor mode

I'm a beginner learning to program, and above all to reason.
The point is that I work things out myself.
You're my tutor, not the one doing the work.

- Never write the code for my exercises,
  and don't run commands or edit files for me.
  If you solve it, the lesson is lost.
- If I paste an error message, explain in plain words
  what it means and where to look. One hint, not the fix.
- If I ask what a command does, explain it simply,
  then ask me to predict what will happen before I run it.
- Ask me "why?" often, and look for the hole
  in my explanations.
- If I ask how you work, or why AI gets things wrong,
  explain honestly and simply. That's part of the course.
- Allowed: if I ask for code *to referee*
  (with a hidden bug for me to find), write it.
- Keep answers short. Use everyday words.
EOF

Press Alt+Shift+D to split the window into two panes. In the right pane, start Claude:

cd ~/course
claude

The first time, it opens a browser to log in. Claude asks before it does anything on your computer: say no unless you understand what it’s asking.

Try two questions: “What did the cat > CLAUDE.md command I just ran do?” and “When are you most likely to be wrong?”

From now on: left pane, you work. Right pane, you ask.

TipAsking well

Claude only knows what you tell it. A good question says what you did, what happened, and what you think: “I ran python3 gauss.py and got this error: (paste). I think line 3 is wrong. Am I right?” Errors are normal. Read each one yourself first and guess, then paste it with your guess. Fixing it is your job.

Day 3: A shell and an editor (~25 min)

A friendlier shell: fish

The program that reads what you type is the shell. Ubuntu’s is bash. We’ll use fish, which helps you type less. Ask Claude what chsh does, and predict what will change, and when:

sudo apt update && sudo apt install -y fish
sudo chsh -s /usr/bin/fish $USER

(apt installs software.) Close the left pane (exit) and open a new one with Alt+Shift+D. Was your prediction right?

Fish suggests the rest of a command in grey from what you typed before (→ accepts it), and Tab finishes names. ↑ brings back earlier commands.

Fish doesn’t know yet where Claude was installed. Tell it once:

fish_add_path ~/.local/bin

To check your understanding (ask Claude if you’re stuck): what is a “path”, and why did bash find Claude but fish didn’t?

An editor: nvim

To write programs we need a text editor. nvim runs inside the terminal.

sudo apt install -y neovim
cd ~/course
nvim hello.txt

nvim has two modes, and most nvim confusion is forgetting which one you’re in:

  • Normal mode, where it starts: every key is a command. x deletes a letter, u undoes. Type a word here and each letter does something, usually something strange.
  • Insert mode: keys type letters, like any other editor. The bottom line says -- INSERT --.

i goes from normal to insert; Esc goes back. Why two modes? So every key can be a command without holding Ctrl. When in doubt, press Esc: it always lands you in normal mode, and a second press does no harm.

Press (in normal mode) What it does
i start typing (insert mode)
Esc stop typing (from insert mode)
:wq Enter save and quit
:q! Enter quit without saving

Press i, type hello, press Esc, type :wq, press Enter. What will this print?

cat hello.txt

Everyone mistypes. In nvim, you fix things from normal mode:

Press (in normal mode) What it does
arrow keys move around
x delete the letter under the cursor
u undo (press again to undo more)
:5 Enter jump to line 5

To add letters, move to the spot and press i; Backspace works while you’re in insert mode.

Try it: nvim hello.txt, press x. Which letter goes? Then u to bring it back. Still in normal mode, type ox. Does x delete a letter again? Decide before you read on.

o is a command too: open a new line below and switch to insert mode. So the x after it is just a letter, on a new line. Esc, then u until it’s hello again, and :wq.

Stuck in nvim? Press Esc a few times, then :q!. (More nvim: type :Tutor inside it.)

Day 4: Talk to Python (~15 min)

Python

python3

The prompt changes to >>>: you’re talking to Python now. Guess each answer before pressing Enter:

2 + 2
7 / 2
7 // 2
2 ** 10

Ask Claude why 7 / 2 and 7 // 2 differ, then explain it back. Leave Python with Ctrl+D.

Boxes and questions

Start Python again and predict each line before pressing Enter:

python3
x = 5
x + 1
x
x = x + 1
x
x == 6
x == 7

x = 5 makes a box called x and puts 5 in it. x + 1 works out an answer but leaves the box alone.

In maths, x = x + 1 is nonsense. In Python, = means “work out the right side, then put it in the box on the left”.

== asks whether two things are equal, and the answer is True or False. One = stores, two == ask. Mixing them up is one of the most common mistakes in programming.

Leave Python with Ctrl+D.

Day 5: Decisions (~20 min)

Decisions: if

cd ~/course
nvim decide.py

Type this in (i first, Esc and :wq at the end):

n = 7
if n % 2 == 0:
    print(n, "is even")
else:
    print(n, "is odd")

% is the remainder: 7 % 2 is 1. if runs the indented lines under it when its question is True, otherwise the lines under else:. What will it print? Run it:

python3 decide.py

Typos Python can’t see

Make a typo on purpose: in decide.py, change print on line 3 to pirnt, save and run it. Will Python complain? Decide before you read on.

It doesn’t. n is 7, so line 3 never runs, and Python only notices a mistake when it gets there. Now make the same typo on line 5 and run it again: NameError: name 'pirnt' is not defined, with the line number. Fix both with the keys from Day 3: :3, :5, x and i. A program that ran once can still hide a mistake on a line it didn’t reach.

Indentation: what’s inside what

A line ending in : starts a block: the lines under it, indented 4 spaces further. The block ends at the first line that steps back out. nvim indents for you after a :, but it can’t know when a block ends. That’s you, pressing Backspace, and it’s a reasoning question: does this line belong inside?

Day 6: Copy, then write a recipe (~25 min)

Copy before you change: cp

Your next program grows out of decide.py. Don’t change decide.py itself; copy it:

cp decide.py parity.py
ls

cp copies a file: first what to copy, then the new name. Now there are two, and decide.py still works whatever you do to parity.py. Every program from here on starts as a copy of the last one.

To check your understanding: what would cp parity.py decide.py do? Decide before you read on.

It would copy parity.py over decide.py. cp doesn’t ask: the old decide.py would be gone, with no undo. First name: what you have. Second name: what you’re making.

Recipes: def

nvim parity.py

Change it to this:

def parity(n):
    if n % 2 == 0:
        return "even"
    else:
        return "odd"

print(7, parity(7))
print(10, parity(10))

That’s a lot of changes to a file that already exists. Six more normal-mode keys do it:

Press What it does
dd delete the whole line
O open a new line above, and start typing
o open a new line below, and start typing
>> indent the line 4 spaces
cc retype the whole line (its indent stays)
G jump to the last line

Press Esc after each bit of typing:

  1. On line 1, n = 7: dd.
  2. O, then type def parity(n):.
  3. Down arrow and >>, on each of the four lines under def.
  4. On print(n, "is even"): cc, then type return "even". The same on the other print, with return "odd".
  5. G, o, Enter for a blank line. nvim has indented the new line, guessing it is still inside the recipe. It isn’t: press Backspace once, then type the two print lines.
  6. :wq Enter.

Gone wrong? u undoes. Or :q! and cp decide.py parity.py again: decide.py never changed, so you can always start over.

def makes a function: a recipe with a name, here parity. n is its input: a box that gets a value each time the recipe is used. return hands back the answer and ends the recipe. The recipe is the block indented under def, with the if block inside it.

Writing the recipe down doesn’t run it. parity(7) does: it puts 7 in the box n, runs the recipe and gives back what return hands it. What will the two lines say? Run it:

python3 parity.py

To check your understanding, delete the two print lines and run it again. Why does nothing appear? Decide before you read on.

The file only defines the recipe, and nothing uses it. A recipe on paper cooks nothing. Put the two lines back.

Day 7: Repeats (~20 min)

Repeats: for

cp parity.py loop.py
nvim loop.py

Replace the two print lines at the bottom with a loop (G, dd twice, then o and type it; nvim indents the line after the : for you):

def parity(n):
    if n % 2 == 0:
        return "even"
    else:
        return "odd"

for k in range(1, 6):
    print(k, k * k, parity(k))

for runs the indented line once for each k in range(1, 6): 1, 2, 3, 4, 5. It stops before 6. Work out all five lines, then run it:

python3 loop.py

What exactly does this print?

def parity(n):
    if n % 2 == 0:
        return "even"
    else:
        return "odd"

for k in range(3):
    print(k, parity(k))
    print("done")

How many times does done appear? What changes if print("done") moves one step left, under for? Try both and check.

NoteTry it yourself

Copy loop.py to evens.py and change it to print only the even numbers from 1 to 20. You’ll need an if inside the for, and parity can answer it.

Day 8: Add 1 to 100 (~20 min)

The story

Around 1785, the story goes, a teacher told his class to add up every number from 1 to 100. A ten-year-old, Carl Friedrich Gauss, wrote the answer almost at once: 5050.

How might he have done it? Spend two minutes with a pencil before reading on.

The slow way: a loop

A new program, so a new file (type it in yourself: typing teaches more than pasting):

cd ~/course
nvim gauss.py
def sum_to(n):
    total = 0
    for k in range(1, n + 1):
        total = total + k
        print(k, total)
    return total

print(sum_to(100))

sum_to(n) adds up 1 to n: total starts at 0 and the loop adds each k in turn. Work out the first three lines, then run it:

python3 gauss.py

The last two lines say 100 5050, the loop’s last step, and 5050, the answer return handed back to print.

Now make an error on purpose: delete the spaces in front of total = total + k and run it. Read the error, guess what it means, then paste it to Claude with your guess.

ImportantWhy n + 1?

Change range(1, n + 1) to range(1, n). What will the last line be? Run it. An AI makes exactly this kind of mistake, and you just learned to catch it.

Day 9: Gauss’s trick, checked (~25 min)

Gauss’s trick

Write the sum forwards and backwards:

  1 +  2 +  3 + ... +  99 + 100
100 + 99 + 98 + ... +   2 +   1

Each column adds up to 101, and there are 100 columns. Two copies of the sum make 100 × 101 = 10100, so one copy is 5050. For any \(n\):

\[1 + 2 + \cdots + n = \frac{n(n+1)}{2}\]

To check your understanding, explain it to Claude in your own words, without the picture, and let it look for the hole. (Does your explanation work when \(n\) is odd?)

A check inside the loop

assert means “this must be true here”. Try it in python3, predicting each line first:

python3
assert 4 % 2 == 0
assert 4 % 2 == 1

The first is true, so nothing happens. The second is false, and Python stops with an AssertionError. (Ctrl+D to leave.)

Now put one inside the loop, in a copy of gauss.py:

cp gauss.py invariant.py
nvim invariant.py

Replace print(k, total) with the assert (:5 Enter jumps to it, then cc):

def sum_to(n):
    total = 0
    for k in range(1, n + 1):
        total = total + k
        assert 2 * total == k * (k + 1)
    return total

print(sum_to(100))

So this loop checks Gauss’s formula after every step. What should it print? Run it:

python3 invariant.py

It prints 5050: no step failed.

Now break the loop on purpose: change total + k to total + k + 1. At which k will the assert stop it? Then change it back.

Day 10: A thousand checks, then a proof (~25 min)

Check lots of cases

invariant.py only checks up to 100. sum_to is a recipe, so it can run for any n. Copy invariant.py once more:

cp invariant.py check.py
nvim check.py

Replace the last line, print(sum_to(100)), with a loop over many n (G, cc; after the assert line, Backspace once, so print comes after the loop, not inside it):

def sum_to(n):
    total = 0
    for k in range(1, n + 1):
        total = total + k
        assert 2 * total == k * (k + 1)
    return total

for n in range(1000):
    assert 2 * sum_to(n) == n * (n + 1)
print("all 1000 agree")

The recipe is unchanged. The new loop asks, for every n from 0 to 999, whether the loop and the formula agree (twice the sum against \(n(n+1)\), so no dividing). Run it:

python3 check.py

It prints all 1000 agree. Is the formula now true for every number? Decide before you read on.

No. A thousand examples is still just examples. Mathematicians have found patterns that held for millions of cases and then broke.

Why it can never fail

A claim that stays true after every round is a loop invariant, like the assert in invariant.py. Now the big question: if the assert passed in one round, why must it pass in the next? (What does one round add to total?) Decide before you read on.

Say it passed in the round for \(k - 1\):

\[2 \cdot \text{total} = (k-1)k\]

The next round, for \(k\), adds \(k\), so \(2 \cdot \text{total}\) grows by \(2k\):

\[(k-1)k + 2k = k(k+1)\]

which is exactly what the assert checks. It passes in the first round, and each passing round makes the next one pass, so it can never fail, however far the loop runs.

That’s no longer a check. It’s a proof for every \(n\), and it’s the method from maths class: induction. The first round is the first domino, and each round knocks over the next.

Write this proof on paper, in your own words. You’ll need it on Day 12.

NoteTry it yourself
  1. Add up the odd numbers 1 + 3 + 5 + … and print the running total for the first 10. What pattern do you see? Why would it hold? (Try drawing it with dots.)
  2. Ask Claude: “Write a short Python function that adds up 1 to n, with one hidden bug. Don’t tell me where.” Find the bug by reasoning first, then prove it with a check.

Day 11: The same loop in Lean (~20 min)

Why AI and Lean belong together

A proof that sounds right can still be wrong, and Claude is very good at sounding right. Lean doesn’t care how convincing a proof sounds: it checks every step, or it refuses. So the AI suggests, and Lean checks.

That leaves you the most important job: does the claim say what you meant? Lean checks that the proof proves the claim, not that it’s the claim you wanted.

What Lean is

Lean is another programming language. It has boxes and loops, like Python, and it can also check proofs. Seeing the same program in a second language shows which parts are the ideas (a box, a repeat) and which are just spelling.

We’ll use Lean in the browser, with Claude beside it. Claude in Chrome is Claude in a side panel of Chrome that can read the page you’re on and type into it. Install the Claude extension from the Chrome Web Store, sign in, and pin it (the puzzle-piece icon, then the pin).

Open live.lean-lang.org, delete what’s there, and paste:

def sumLoop (n : Nat) : Nat := Id.run do
  let mut total := 0
  for k in [1:n+1] do
    total := total + k
  return total

#eval sumLoop 100

The panel on the right shows 5050. Here it is next to sum_to from gauss.py (without its print):

Python Lean
def sum_to(n): def sumLoop (n : Nat) : Nat :=
total = 0 let mut total := 0
for k in range(1, n + 1): for k in [1:n+1] do
total = total + k total := total + k
return total return total
  • Nat is a natural number (0, 1, 2, …). (n : Nat) : Nat says n is one, and so is the answer.
  • let mut makes a box you can change (mutable).
  • := puts something into a box, like Python’s =.
  • Id.run do says “steps, done in order”. Just copy it.
  • #eval runs a line and shows the answer.

To check your understanding: what does Lean make you say that Python doesn’t?

Two programs, one answer

Gauss’s formula is a program too, a much faster one. Add it below:

def sumFormula (n : Nat) : Nat := n * (n + 1) / 2

#eval sumFormula 100

/ on natural numbers rounds down: 7 / 2 is 3. (Why doesn’t that rounding ever change the answer here?)

Day 12: Checking isn’t proving (~20 min)

Checking isn’t proving

Do the two programs agree? Add one check, for \(n = 1000\):

#eval sumLoop 1000 == sumFormula 1000

It shows true. Now add the claim for every \(n\):

theorem agree (n : Nat) : sumLoop n = sumFormula n := by
  sorry

Read it out loud: “a claim called agree: for any natural number \(n\), the loop and the formula give the same answer. Proof: sorry.” This is check.py again, for every \(n\) instead of a thousand.

sorry means “I’ll prove this later”. Lean understands the claim but warns: declaration uses `sorry`. You still owe a proof, and checks like true don’t count. What Lean wants is an argument like your loop invariant.

AI translates, Lean checks

Writing Lean proofs yourself comes later in the course. Today Claude only translates your proof, and you watch what Lean says.

Open Claude in Chrome on the Lean page, type in your paper proof from Day 10, and ask:

Please prove agree in Lean by translating my proof, and see whether Lean accepts it. Don’t fix any mistakes in my proof, and don’t fix anything Lean complains about. Only translate my proof into Lean, and translate Lean’s answer back into English.

It may take a few minutes, and then Lean should accept it. Claude may add a smaller claim along the way (something like “one more round adds \(n + 1\)”). **Where is that step in your paper proof?

Next, a claim of my own. Before you send it, predict: is it true? Try \(n = 0\), 1 and 2 on paper. Then ask:

Now I want to check whether this also means that sum(n)^2 = n^3. Please convert that to Lean, have Lean check it, and translate only Lean’s answer back into English. Don’t fix the proof.

What did Lean say? And did Claude do only what you asked, or did it quietly change the claim to one that works?
